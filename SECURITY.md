# Security

## What SlopBar can access

SlopBar reads the sign-in files that Claude Code and Codex already keep on your PC, in your Windows profile and in each WSL distro. The existing account-switching vault copies full login data, including refresh tokens, into JSON files under `%APPDATA%\dev.thelio.slopbar\accounts`. **That legacy vault is still plaintext.** This telemetry fix does not encrypt or redesign it.

Independent monitoring requires a separate official CLI sign-in. SlopBar rejects a monitoring login whose refresh token equals a known CLI login and verifies that its account and organization match the selected slot. A successful monitoring login is stored separately under `monitoring`, protected by Windows DPAPI for the current Windows user. It is never used for account switching or exported to a CLI. Temporary CLI sign-in files are removed after completion/failure/timeout; an abrupt app or machine crash can leave a temporary `.slopbar-login-*` folder in the selected profile. WSL login folders are restricted to their owner before authentication runs.

Sign-in removes inherited `CLAUDE_*`, `ANTHROPIC_*`, `CODEX_*`, and `OPENAI_*` overrides. Windows disables cmd AutoRun and sets both Claude config and secure-storage directories to the temporary folder. WSL runs the CLI through `env -i` with an allowlist after loading the user's login profile. Both run from the temporary folder; Claude uses `--setting-sources user` to exclude project/local settings and load user settings only from that isolated config. This prevents ordinary profile exports and ancestor project settings from redirecting authentication. Provider-managed policies still apply. A failed import attempts the CLI's logout with that same isolated environment before removing the folder. If Claude uses Credential Manager rather than writing its credentials file, import currently fails and takes this cleanup path; native Credential Manager discovery/import is not implemented.

On Windows, sign-in and isolated logout start suspended, join a kill-on-close job object, then resume. Failure to attach or resume aborts the process before sign-in can run or spawn children. WSL process termination still needs a native integration test. Before returning any successful login, SlopBar atomically persists an imported marker, then attempts to delete its credential file and temporary directory. Failure to persist the marker prevents handoff. Failure to delete cannot make startup cleanup revoke the exported login.

Startup cleanup removes recognized abandoned folders older than 15 minutes. It only attempts logout for a newly marked pending login whose token does not match a saved account/monitoring session; unreadable credentials or monitoring storage disable cleanup revocation. Exported folders and legacy folders without a trustworthy handoff state are deleted locally without server logout. This can leave a legacy abandoned session valid at the provider; revoke unwanted sessions in provider account settings. Cleanup requires the exact generated name and either its ownership marker or a regular legacy CLI credentials file, and excludes directory/credential symlinks. Unrecognized folders are left alone. Concurrent connect, disconnect and account removal share an account reservation through their final disk mutation.

Only independently owned monitoring sessions are refreshed. Imported CLI refresh tokens are never sent to a token endpoint. Refreshes are serialized; new refresh tokens are saved atomically before normal polling resumes, using Windows write-through replacement. If a write fails after rotation, the new token is retained in memory and persistence is retried without replaying the old token. Exiting before that write succeeds can require reconnecting. A transport failure before success headers permits one replay after five minutes; its budget and backoff are persisted. Explicit rejection is terminal. A successful response whose body cannot be read/decoded is terminal too: the consumed token is never replayed. A second uncertain result stops automatic replay and offers reconnecting. Replay may trigger provider reuse detection; its scope across independent sessions is not publicly guaranteed and needs live testing. Saved scopes are preserved. Imported refresh-token deadlines can be synthesized by the CLI and only trigger renewal, not automatic disconnection; a successful refresh clears the old hint unless the response supplies a new lifetime. SlopBar does not invent a lifetime for an omitted refresh response field. HTTP redirects are disabled for authentication and usage requests; token values and response bodies are not returned to the UI.

When an active account's monitor is unavailable, usage can fall back to the CLI access token captured from its current login. This is a read-only usage request and does not refresh/revoke the CLI session or bypass a usage rate limit. The monitoring failure remains separately visible while successful usage is fresh and eligible for balancing. Inactive accounts continue to require their independent session.

A refresh-expiry hint can trigger renewal while the monitoring access token is still usable. Temporary errors, token-endpoint rate limits, and uncertain sends retain that access token for usage requests during backoff, without increasing the persisted replay budget. Expired or usage-rejected access tokens are withheld. Explicit refresh rejection and an unreadable successful response still stop access immediately.

Disconnect removes local monitoring credentials even when the provider is unavailable, then attempts revocation of that monitoring token. Replacing a monitoring login saves the new login first and attempts revocation of the old chain. Server revocation is best effort; a failed disconnect revocation is reported in the UI. Account removal also attempts revocation. Imported CLI sessions are never revoked by these actions.

Wrong-account or storage failures after login handoff attempt revocation of the uninstalled login. The ownership check and revocation share the monitoring lock, and tokens matching known CLI or in-memory/persisted monitoring sessions are protected. Shared-login rejection never invokes this cleanup. Unreadable ownership storage suppresses revocation; an offline provider or ambiguous ownership can leave a session to revoke manually in provider account settings. WSL write-through marker replacement still needs a real WSL integration check and fails closed if unsupported.

Authentication and usage requests go over HTTPS directly to the providers: `api.anthropic.com` and `platform.claude.com` for Claude, `chatgpt.com` and `auth.openai.com` for Codex. Monitoring does not send model prompts. The usage cache contains readings and timestamps, not authentication tokens. The non-Windows headless test build uses owner-only files rather than DPAPI; the desktop app targets Windows.

These OAuth sessions are credentials, not read-only usage API keys. DPAPI protects files at rest, but a compromised SlopBar process or code running as the same user can still misuse them. This change does not eliminate application, dependency, or update supply-chain risk.

Local builds have upstream updates disabled at compile time. Official release builds explicitly enable `upstream-updates`; those updates must match the signing key built into the app. Signatures authenticate a publisher, not the safety of a release.

## Reporting a vulnerability

Please report upstream security issues privately through [GitHub's private vulnerability reporting](https://github.com/thelioo/slopbar/security/advisories/new) instead of opening a public issue.

## Diagnostic reports

Diagnostic collection uses structured allowlisted events rather than free-form logs. Exported reports contain anonymous account numbers, usage percentages/timestamps, operational outcomes, and build metadata. Never attach the account vault, monitoring sessions, or `diagnostics/history.bin` to a support request; use Settings' **Export diagnostics** report.

Tokens, account identities, aliases, paths, distro names, HTTP URLs/headers/bodies, raw errors, and stacks are excluded from export. A local account-ID-to-number mapping enables continuity across restarts. It remains inside the Windows DPAPI-protected journal and is never exported. On Unix headless tests the journal is private but not encrypted. Reports are readable JSON, remain on the machine until explicitly shared, and include usage/timing information. No diagnostic upload endpoint exists.

Events are bounded by 7 days and 10,000 entries; the local mapping is capped at 1,024 accounts. Corrupt/unreadable history and failed persistence are reported without blocking account monitoring. Diagnostic retention does not include old exports; users control those files. Deleting the app's diagnostics folder while SlopBar is stopped clears its history and mapping. Unchanged routine observations are suppressed with hourly heartbeats; real changes are recorded. Usage deduplication tracks monitoring, CLI and active-CLI fallback independently, preserving each origin’s failures and recoveries. The report shows its actual oldest record, suppressed observations, discarded events and journal-write count. Serialization, DPAPI and disk I/O run in a coalescing background writer. Routine changes are written at most once per five minutes when needed; auth/lifecycle transitions request an immediate write. Only export and orderly shutdown wait for queued writes. Abrupt termination can lose queued auth transitions and up to five minutes of routine changes. All diagnostic persistence remains best effort and is separate from mandatory monitoring-token persistence.
