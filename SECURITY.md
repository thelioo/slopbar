# Security

## What SlopBar can access

SlopBar reads the sign-in files that Claude Code and Codex already keep on your PC, in your Windows profile and in each WSL distro. The account-switching vault keeps a copy of each account's full CLI login, including refresh tokens, in one `.slot` file per account under `%APPDATA%\dev.thelio.slopbar\accounts`, encrypted with Windows DPAPI for the current Windows user. Earlier releases wrote these as plaintext `.json` files. On each start SlopBar encrypts any it finds: it writes the encrypted copy, reads it back and compares it, and only then deletes the plaintext file. If any step fails, the plaintext file stays where it is (for one release SlopBar still reads plaintext slots, and the newer of the two copies wins), the attempt is retried at the next start, and the diagnostics journal records how many slots were migrated, failed or unreadable (counts only). Settings > Health warns while any plaintext slot remains. Files that are not readable slots are left untouched. Deleting a file does not overwrite the disk blocks it used, so a plaintext copy can remain recoverable from the disk until they are reused. The one-time copy from a Usage Bar install leaves Usage Bar's own data folder in place, including its plaintext vault; delete it once SlopBar works. The non-Windows headless test build stores slots as owner-only files, not encrypted.

Independent monitoring requires a separate official CLI sign-in. SlopBar rejects a monitoring login whose refresh token equals a known CLI login and verifies that its account and organization match the selected slot. A successful monitoring login is stored separately under `monitoring`, protected by Windows DPAPI for the current Windows user. It is never used for account switching or exported to a CLI. Temporary CLI sign-in files are removed after completion/failure/timeout; an abrupt app or machine crash can leave a temporary `.slopbar-login-*` folder in the selected profile. WSL login folders are restricted to their owner before authentication runs.

Sign-in removes inherited `CLAUDE_*`, `ANTHROPIC_*`, `CODEX_*`, and `OPENAI_*` overrides. Windows disables cmd AutoRun and sets both Claude config and secure-storage directories to the temporary folder. WSL runs the CLI through `env -i` with an allowlist after loading the user's login profile. Both run from the temporary folder; Claude uses `--setting-sources user` to exclude project/local settings and load user settings only from that isolated config. This prevents ordinary profile exports and ancestor project settings from redirecting authentication. Provider-managed policies still apply. A failed import attempts the CLI's logout with that same isolated environment before removing the folder. If Claude uses Credential Manager rather than writing its credentials file, import currently fails and takes this cleanup path; native Credential Manager discovery/import is not implemented.

**Sign-in window** (Settings > Accounts). By default a sign-in on Windows opens its web page in a browser profile kept per email under `%LOCALAPPDATA%\dev.thelio.slopbar\signin-profiles\<hash>`. The folder is named by the first 16 hex characters of the SHA-256 of the lowercased email, so the email is not in its name. SlopBar starts Chrome (else Edge) with `--user-data-dir` set to that folder. These folders hold whatever the browser keeps for the sites signed in there, which means Google and provider session cookies. They stay on this PC, outside the roaming profile, and are never in a backup or a diagnostics export. **Forget sign-in profiles** deletes them all; a profile whose browser is still open cannot be deleted until its windows are closed. Deleting them signs nothing out of SlopBar. The alternatives are a private window (`--inprivate` / `--incognito`, which keeps nothing once the private session closes) and the default browser, as the CLIs open it. SlopBar never types into, reads or approves these pages, and it stores no Google credential: the user completes every page. Claude Code is pointed at the page through `BROWSER`, which names `slopbar.exe`, with `SLOPBAR_SIGNIN_TARGET` naming the window. Started that way, `slopbar.exe` opens only `https` pages of `claude.ai`, `claude.com`, `anthropic.com`, `openai.com` or `chatgpt.com` (no credentials or port in the URL), and only into a profile folder directly under `signin-profiles`, then exits. When the expected email is plain address characters, Claude's `--email` prefills it. Codex ignores `BROWSER` on Windows, so its sign-in runs through the CLI's own app server (`codex app-server`, `account/login/start`), which returns the authorization URL without opening a browser. The login still lands in the isolated temporary `CODEX_HOME` with file credential storage and is imported as before; an older Codex without the app server falls back to `codex login`. Codex's email is not prefilled. The sign-in's kill-on-close job allows breaking away only for a Claude sign-in that opens a profile or private window, so the browser outlives the sign-in. The CLI processes do not ask to break away and still end with the job. Sign-ins in WSL open the page as the CLI does.

**Sign in all accounts** (after a restore). A restore records the accounts it names that are not signed in here in `pending-signins.json` in the app's data folder: provider, account id and email, never sign-in data. The action runs one sign-in at a time, grouped by email. A pending account's sign-in is saved to the vault only when the signed-in account and organization match its id; any other login is not saved, and its fresh session is revoked as a wrong-account monitoring login is. Monitoring sign-ins keep every protection described above.

On Windows, sign-in and isolated logout start suspended, join a kill-on-close job object, then resume. Failure to attach or resume aborts the process before sign-in can run or spawn children. WSL process termination still needs a native integration test. Before returning any successful login, SlopBar atomically persists an imported marker, then attempts to delete its credential file and temporary directory. Failure to persist the marker prevents handoff. Failure to delete cannot make startup cleanup revoke the exported login.

Startup cleanup removes recognized abandoned folders older than 15 minutes. It only attempts logout for a newly marked pending login whose token does not match a saved account/monitoring session; unreadable credentials or monitoring storage disable cleanup revocation. Exported folders and legacy folders without a trustworthy handoff state are deleted locally without server logout. This can leave a legacy abandoned session valid at the provider; revoke unwanted sessions in provider account settings. Cleanup requires the exact generated name and either its ownership marker or a regular legacy CLI credentials file, and excludes directory/credential symlinks. Unrecognized folders are left alone. Concurrent connect, disconnect and account removal share an account reservation through their final disk mutation.

Only independently owned monitoring sessions are refreshed. Imported CLI refresh tokens are never sent to a token endpoint. Refreshes are serialized; new refresh tokens are saved atomically before normal polling resumes, using Windows write-through replacement. If a write fails after rotation, the new token is retained in memory and persistence is retried without replaying the old token. Exiting before that write succeeds can require reconnecting. A transport failure before success headers permits one replay after five minutes; its budget and backoff are persisted. Explicit rejection is terminal. A successful response whose body cannot be read/decoded is terminal too: the consumed token is never replayed. A second uncertain result stops automatic replay and offers reconnecting. Replay may trigger provider reuse detection; its scope across independent sessions is not publicly guaranteed and needs live testing. Saved scopes are preserved. Imported refresh-token deadlines can be synthesized by the CLI and only trigger renewal, not automatic disconnection; a successful refresh clears the old hint unless the response supplies a new lifetime. SlopBar does not invent a lifetime for an omitted refresh response field. HTTP redirects are disabled for authentication and usage requests; token values and response bodies are not returned to the UI.

When an active account's monitor is unavailable, usage can fall back to the CLI access token captured from its current login. This is a read-only usage request and does not refresh/revoke the CLI session or bypass a usage rate limit. The monitoring failure remains separately visible while successful usage is fresh and eligible for balancing. Inactive accounts continue to require their independent session.

A refresh-expiry hint can trigger renewal while the monitoring access token is still usable. Temporary errors, token-endpoint rate limits, and uncertain sends retain that access token for usage requests during backoff, without increasing the persisted replay budget. Expired or usage-rejected access tokens are withheld. Explicit refresh rejection and an unreadable successful response still stop access immediately.

Disconnect removes local monitoring credentials even when the provider is unavailable, then attempts revocation of that monitoring token. Replacing a monitoring login saves the new login first and attempts revocation of the old chain. Server revocation is best effort; a failed disconnect revocation is reported in the UI. Account removal also attempts revocation. Imported CLI sessions are never revoked by these actions.

**Revoke all SlopBar sessions** (on each account in Settings, and the agents' `revoke_account_sessions`, which only reports unless called with `confirm: true`) revokes every sign-in SlopBar itself holds for that account: the monitoring session is revoked at the provider and deleted here. The CLI's own sign-in belongs to the CLI and stays signed in; sign it out with `claude /logout` or `codex logout`. The action offers to also remove SlopBar's saved copy of that login from the vault, as Remove does (not while the account is in use).

Settings > Health and the account row report sign-in health per account: a monitoring sign-in the provider rejected, and a CLI login whose access token the provider rejected (an HTTP 401 on a usage read). The CLI flag clears as soon as the CLI renews its login or a read with it succeeds. SlopBar never renews or replaces the CLI's login; it tells the user to sign the CLI in again.

Wrong-account or storage failures after login handoff attempt revocation of the uninstalled login. The ownership check and revocation share the monitoring lock, and tokens matching known CLI or in-memory/persisted monitoring sessions are protected. Shared-login rejection never invokes this cleanup. Unreadable ownership storage suppresses revocation; an offline provider or ambiguous ownership can leave a session to revoke manually in provider account settings. WSL write-through marker replacement still needs a real WSL integration check and fails closed if unsupported.

Authentication and usage requests go over HTTPS directly to the providers: `api.anthropic.com` and `platform.claude.com` for Claude, `chatgpt.com` and `auth.openai.com` for Codex. Monitoring does not send model prompts. The usage cache contains readings and timestamps, not authentication tokens. The non-Windows headless test build uses owner-only files rather than DPAPI; the desktop app targets Windows.

These OAuth sessions are credentials, not read-only usage API keys. DPAPI protects files at rest, but a compromised SlopBar process or code running as the same user can still misuse them. This change does not eliminate application, dependency, or update supply-chain risk.

Local builds have upstream updates disabled at compile time. Official release builds explicitly enable `upstream-updates`; those updates must match the signing key built into the app. Signatures authenticate a publisher, not the safety of a release.

## What leaves this machine

SlopBar has no telemetry: no analytics, crash reporting service, usage pings or server of its own. Only these connections are made, and each goes straight to the party named:

- **Provider usage and billing endpoints, with your own tokens.** Claude: `api.anthropic.com` (usage, profile) and `platform.claude.com` (monitoring token renewal and revocation). Codex: `chatgpt.com` (usage, banked resets, account record) and `auth.openai.com` (monitoring token renewal and revocation). Sign-ins run the providers' own CLIs. Requests carry only what each endpoint needs to answer about your account.
- **Optional in-use sharing.** When you choose a synced folder or an rclone remote under Settings > Data, SlopBar writes one small file per computer there: a random machine id, the computer's name, a timestamp and, for each account signed in, a hash of the provider and account id with where it is signed in (for example "Windows" or "WSL: Ubuntu"). No emails, tokens or usage numbers. The files go only where you pointed SlopBar; the sync client or rclone carries them to your other computers. Sharing is off by default.
- **Optional account roster.** Off by default. Turned on under Settings > Data > Other computers (or `account_roster` through `update_settings`), each SlopBar also writes `SlopBar/roster/<machine id>.roster` to the same folder or rclone remote: its computer name and, for each account signed in, the provider, account id, email and plan. Never sign-ins, tokens or anything else from the vault. Because it names accounts, the file is encrypted like a backup (XChaCha20-Poly1305, key from Argon2id at 64 MiB and 3 passes, random salt and nonce, authenticated header) with a roster passphrase the user sets on each computer; the passphrase is kept in its own file protected with Windows DPAPI, never in `settings.json`, a backup or a diagnostics export. A roster that does not open with this computer's passphrase is counted in Health and otherwise ignored. Accounts other computers' rosters name that are not signed in here are offered to "Sign in all accounts", which still runs each CLI's own sign-in for the user to complete. Turning the roster off deletes this computer's file.
- **Optional phone alerts.** Off by default. Turned on under Settings > Notifications > Phone, a few notifications (a plan renewing within a day, unexpected use, a runaway agent, a limit reached; the user picks which) are also posted over HTTPS to the ntfy topic URL the user entered: ntfy.sh or a self-hosted server (plain http is accepted only for a server on this machine or the local network). Each message carries a title, a line of text, a tag and a priority. Unless "Include account names" is ticked, the text names only the provider ("A Codex plan renews tomorrow"), never an alias, email or account id. The optional access token is sent as a bearer token to that server only (redirects are not followed) and is stored in its own file protected with Windows DPAPI, never in `settings.json` or a backup. Anyone who knows a public ntfy.sh topic can read it, so the topic should be hard to guess or on a server the user controls. "Send test" sends one message on demand.
- **Update checks, only in builds with automatic updates.** Official release builds check the release manifest on GitHub (`github.com/thelioo/slopbar/releases`) and download signed updates from there. Local builds, including any you compile yourself, have updates disabled at compile time and make no update requests.

Nothing else is sent. Opening a provider's billing or security page hands its fixed URL to your browser. Settings > Health is computed from what SlopBar already knows and adds no requests. Diagnostics exports and crash records stay on this machine until you share an export yourself.

**Backups** (Settings > General > Backup, or the agents' `export_backup`) are files the user saves and moves themselves; SlopBar uploads them nowhere. One holds settings (aliases, plan details, project pins, preferences, the phone-alert topic URL), the weekly usage history, the spend ledger and each account's provider, id and email. It never holds sign-ins: no saved CLI logins from the vault, monitoring sessions, refresh or access tokens, or the phone-alert token, so accounts are reconnected after a restore. The contents are encrypted with XChaCha20-Poly1305 under a key derived from the user's passphrase with Argon2id (64 MiB, 3 passes; RustCrypto's `chacha20poly1305` and `argon2` crates) with a random salt and nonce per file; the header is authenticated too, so a changed byte anywhere makes the file refuse to open. The passphrase is never stored or logged. Restoring (`restore_backup` previews unless called with `dry_run: false`) checks the format and version, shows what changes, and merges: accounts are matched by provider and id, and data for accounts not signed in here is kept until they are reconnected.

**Crash records** are off by default. Turned on (Settings > General > Diagnostics, or `crash_records` through `update_settings`), a panic adds one entry to the local diagnostics journal: the source file within SlopBar's own code (anything else is recorded only as "dependency", "std" or "other"), the line, and the kind of thread. The panic's message, paths outside the source tree and thread names are never recorded, since a message can contain anything. Entries follow the journal's retention and appear in exports.

## Reporting a vulnerability

Please report upstream security issues privately through [GitHub's private vulnerability reporting](https://github.com/thelioo/slopbar/security/advisories/new) instead of opening a public issue.

## Diagnostic reports

Diagnostic collection uses structured allowlisted events rather than free-form logs. Exported reports contain anonymous account numbers, usage percentages/timestamps, operational outcomes, and build metadata. Never attach the account vault, monitoring sessions, or `diagnostics/history.bin` to a support request; use Settings' **Export diagnostics** report.

Tokens, account identities, aliases, paths, distro names, HTTP URLs/headers/bodies, raw errors, and stacks are excluded from export. A local account-ID-to-number mapping enables continuity across restarts. It remains inside the Windows DPAPI-protected journal and is never exported. On Unix headless tests the journal is private but not encrypted. Reports are readable JSON, remain on the machine until explicitly shared, and include usage/timing information. No diagnostic upload endpoint exists.

Events are bounded by 7 days and 10,000 entries; the local mapping is capped at 1,024 accounts. Corrupt/unreadable history and failed persistence are reported without blocking account monitoring. Diagnostic retention does not include old exports; users control those files. Deleting the app's diagnostics folder while SlopBar is stopped clears its history and mapping. Unchanged routine observations are suppressed with hourly heartbeats; real changes are recorded. Usage deduplication tracks monitoring, CLI and active-CLI fallback independently, preserving each origin’s failures and recoveries. The report shows its actual oldest record, suppressed observations, discarded events and journal-write count. Serialization, DPAPI and disk I/O run in a coalescing background writer. Routine changes are written at most once per five minutes when needed; auth/lifecycle transitions request an immediate write. Only export and orderly shutdown wait for queued writes. Abrupt termination can lose queued auth transitions and up to five minutes of routine changes. All diagnostic persistence remains best effort and is separate from mandatory monitoring-token persistence.
